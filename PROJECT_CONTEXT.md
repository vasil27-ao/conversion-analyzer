# Контекст проекта

Этот файл — постоянная память о проекте. Его нужно обновлять при значимых решениях и изменениях статуса.

## Что мы делаем

Разрабатываем сервис «Анализатор конверсионности страниц»: пользователь вставляет ссылку на страницу, сервис прогоняет её через AI-агента, обученного оценивать конверсию по определённой методике, и выдаёт отчёт с оценками и беклогом задач для команды.

Полное содержание требований — в `docs/technical-spec.md` (рабочая копия исходного ТЗ).

## Зачем

Чтобы автоматизировать ручную работу CRO-специалиста по оценке конверсионности страниц (первый экран, оффер, доверие, форма/CTA, мобильная версия и т.д.) и получать воспроизводимые, обоснованные оценки вместо разового ручного разбора.

## Моя роль

Проект создаётся в рамках стажировки на позицию Product Manager. Работа ведётся с активным использованием Cursor/AI.

## Источник требований

Исходный источник требований — приложенное техническое задание («Анализатор конверсионности страниц», версия 1.0, дата 07.08.2026, постановщик — Marvis (PM), исполнитель — стажёр-разработчик). Рабочая копия текста — `docs/technical-spec.md`. Исходный `.docx`-файл не изменяется.

## Формат работы

Проект выполняется поэтапно. Этапы согласно ТЗ (раздел 9):

1. Разработка чек-листа методики и согласование с PM.
2. Промпт агента + проверка на 3 тестовых страницах.
3. Бэкенд: приём URL, сбор данных страницы, вызов агента, сохранение результата.
4. Фронтенд: форма ввода, статус, экран отчёта, выгрузка файла.
5. Сборка и проверка по критериям приёмки (раздел 8 ТЗ).

Переход к следующему этапу — только по явному указанию PM (пользователя).

## Текущий статус

Этап 1 (разработка чек-листа методики): чек-лист из 6 блоков и 20 критериев со шкалой оценки 0/1/2/N/A разработан, прошёл внутреннюю ревизию; финальные уточнения PM по N/A vs 0 и анализу без скриншотов внесены в `docs/cro-methodology.md`.

Этап 2 (промпт агента + проверка на 3 тестовых страницах): системный промпт (`backend/app/agent/prompts/system_prompt.md`) содержит методику и формат ответа LLM. Архитектура: один вызов LLM → валидация → детерминированный overall и score блоков на backend → `AgentResult`. LLM даёт критерии, `what_is_wrong`/`why_it_matters` по блокам, problems, backlog и `overall.summary` (2–3 предложения). Реальные прогоны с Gemini выполнены на этапе 5.

Этап 3 (backend API): **завершён на уровне backend MVP**. Рабочий API: `POST /api/analyses`, `GET /api/analyses/{id}`, `GET /api/health`; wiring SQLite + `AGENT_IMPL` (mock/gemini); orchestrator pending → running → done/failed.

Этап 4 (frontend): **завершён на уровне frontend MVP**. Vite + React + TypeScript в `frontend/`: форма URL → polling статуса → экран отчёта (overall, 6 блоков, problems, backlog) → скачивание standalone HTML → новый анализ. Backend дополнен CORS для локального Vite и полем `url` в ответе статуса.

Этап 5 (сборка и приёмка): **завершён**. `AGENT_IMPL=gemini`; полный E2E через frontend; три тестовые страницы разного качества с разными обоснованными оценками; ошибки недоступной страницы и сбоя агента обрабатываются без падения сервиса; standalone HTML-отчёт скачивается.

Публикация: репозиторий https://github.com/vasil27-ao/conversion-analyzer; frontend — https://conversion-analyzer.vercel.app (`VITE_API_BASE`); backend — https://conversion-analyzer-production.up.railway.app (Docker + Playwright Chromium). CORS задаётся через `CORS_ORIGINS`.

## Область первой версии методики

Первая версия методики ограничена **лендингами**. Это рабочее ограничение для разработки первой версии чек-листа, а не изменение исходного ТЗ и не окончательное ограничение всего сервиса — расширение на другие типы страниц не исключается в будущем.

## Принятые решения

- Первую версию методики разрабатываем на материале лендингов (рабочее ограничение этапа 1, не сужение ТЗ).
- За основу чек-листа приняты 6 блоков и 20 критериев, согласованные в чате (см. `docs/cro-methodology.md`): первый экран и оффер; понятность ценности продукта; доверие; форма/целевое действие; мобильная версия; отвлекающие элементы.
- Критерии оценивают не только наличие элемента, но его понятность и полезность в контексте страницы; применимость каждого элемента зависит от типа лендинга.
- Оценивается только то, что можно определить по данным страницы, доступным сервису (см. ниже решение про отказ от скриншотов).
- Скорость загрузки пока не входит в чек-лист — нет надёжного способа её измерить по текущим данным.
- Динамические элементы, не попавшие в собранные данные (например, попапы с задержкой), на первой итерации не оцениваются.
- Разработана шкала оценки 0/1/2/N/A для всех 20 критериев: смысл уровней единый для всего чек-листа, конкретные признаки 0/1/2 определены индивидуально под каждый критерий, оценка обязательно подтверждается наблюдением из данных страницы.
- Финальное правило N/A vs 0 (согласовано с PM 2026-08-10): если критерий применим и элемент ожидается для конкретного лендинга, но отсутствует — это 0, а не N/A. N/A — только если критерий объективно неприменим к типу предложения или его нельзя оценить по доступным данным. Временное правило и связанный открытый вопрос закрыты.
- Сервис не создаёт и не анализирует скриншоты страницы (согласовано с PM 2026-08-10). Анализ строится на коде и структуре страницы: HTML/DOM, видимый текст, а для визуально-зависимых критериев — данные отрендеренной страницы после выполнения JavaScript (DOM, computed styles, координаты и размеры элементов, видимость, положение относительно viewport, desktop/mobile layout). Открытый вопрос про full-page/viewport скриншоты закрыт как неактуальный.
- Технологический стек зафиксирован: Python, FastAPI (backend/API), Playwright (рендеринг страницы и получение DOM/структурированных данных, без снятия скриншотов), SQLite (хранение результатов первой версии). PM подтвердил отсутствие ограничений по стеку; выбор сделан нами и зафиксирован как решённый.
- Архитектура MVP-отчёта (2026-08-10, **наше** архитектурное решение, не решение PM): один вызов LLM; backend валидирует состав ответа (6 блоков / 20 id), считает `overall.score`/`level` и `blocks[].score` по одной формуле с равными весами и порогами 50/75; LLM пишет `overall.summary` (2–3 предложения) и аналитику блоков (`what_is_wrong`, `why_it_matters`). Модели: `LlmAgentResult` → `AgentResult`. Формат отчёта: score+level, summary, топ-3 backlog, 6 блоков, problems, backlog.
- Frontend MVP (2026-08-10): Vite + React + TypeScript; отчёт скачивается как standalone HTML на клиенте из уже сохранённого результата API (отдельный backend-endpoint экспорта не добавлен).
- Этап 5 / приёмка (2026-08-10): рабочие прогоны на Gemini; тестовый набор — `https://example.com` (слабая), `https://www.w3schools.com/` (средняя), `https://stripe.com/` (сильная). Для клиентского UI технические формулировки (`layout`, `HTML`, `DOM`, `mock` и т.п.) нормализуются на frontend (`presentClientText`).
- Доработка перед публикацией (2026-08-10): обрезка большого HTML для LLM — head+tail (не только первые N символов); в промпт уточнено, что нельзя уходить в массовый N/A через переклассификацию страницы («документация/заглушка»). Остаточная вариативность LLM по соседним баллам (0/1/2) и редким пограничным N/A сохраняется как ограничение.
- Деплой (2026-08-10): frontend на Vercel; backend на Railway в Docker-образе Playwright (Chromium). Связка через `VITE_API_BASE` и `CORS_ORIGINS`.
- Сбор страниц (2026-08-11): Chromium для коллектора поднимается вне `playwright.launch` и подключается по CDP — иначе antibot вроде Ozon FAB отвечает 403 и блокирует автоматизацию; после challenge коллектор ждёт реальный контент, а не падает на первом 403. На Railway датацентровый IP Ozon может отдельно резать (`нет соединения` / VPN); для этого опционален `COLLECTOR_PROXY_SERVER`.
- LLM (2026-08-11): основной Gemini; бесплатный запасной — OpenRouter/Qwen (`OPENROUTER_API_KEY`, модель `OPENROUTER_MODEL`). При обоих ключах и `AGENT_IMPL=gemini` включается failover `Gemini → OpenRouter → Gemini` на временных сбоях без длинных пауз. Позже платный ключ заказчика можно поставить основным через env.

Подробности решений — в `docs/decisions.md`.

## Важные ограничения

- Технологический стек согласован (см. «Принятые решения» выше): Python, FastAPI, Playwright, SQLite. Для агента-аналитика в MVP используется Gemini (`AGENT_IMPL=gemini`, модель по умолчанию `gemini-3.6-flash`).
- Повторные прогоны одной страницы могут давать небольшой разброс баллов и редкие пограничные N/A (естественная вариативность LLM); детерминированы только backend-расчёт overall и валидация состава ответа.
- Системный промпт агента и чек-лист методики должны храниться отдельным файлом/конфигом, а не быть зашиты в код.
- Ключ от LLM-провайдера хранится в переменных окружения, не в коде и не в репозитории.
- Не входит в задачу на первой итерации (раздел 7 ТЗ): массовый анализ, сравнение отчётов во времени, интеграция с рекламными кабинетами/аналитикой, автоматическое внедрение рекомендаций на сайт. Архитектуру не стоит делать так, чтобы это было прямо исключено, но реализовывать пока не нужно.
- Если что-то в ТЗ непонятно или на практике оказывается не так — не додумывать самостоятельно, а задавать вопрос PM (особенно по формулировкам пунктов методики и формату итогового файла отчёта).
