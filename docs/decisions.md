## 2026-08-08 — Общие принципы оценки по чек-листу

- Контекст: нужно избежать необоснованных утверждений о влиянии на конверсию и избежать формального подхода «есть/нет элемента».
- Решение: критерии не утверждают, что элемент гарантированно повышает или снижает конверсию (сервис не получает данные аналитики поведения пользователей); оценивается понятность и полезность элемента в контексте страницы, а не только его наличие; применимость критерия зависит от типа лендинга; агент обосновывает оценку тем, что реально увидел на странице; при неприменимости или невозможности корректно оценить критерий используется отметка N/A вместо придуманной оценки.
- Статус: согласовано с PM.

## 2026-08-08 — Динамические элементы вне данных не оцениваются

- Контекст: скриншоты статичны и снимаются на момент загрузки страницы, поэтому элементы, появляющиеся с задержкой или по условию (например, попап при попытке уйти со страницы), могут не попасть в собранные данные.

- Статус: согласовано с PM.

## 2026-08-08 — Шкала оценки критериев: 0/1/2/N/A

- Контекст: по ТЗ (раздел 5) ориентир — шкала 0–2 (реализовано плохо / частично / хорошо), но нужен единый принцип применения к разным критериям и способ работы с неприменимыми/неоцениваемыми пунктами.
- Решение: принята шкала 0/1/2/N/A. Смысл уровней единый для всех критериев: 2 — элемент выполняет свою функцию без потерь для понимания/доверия/действия пользователя; 1 — элемент присутствует и узнаваем, но выполнен с наблюдаемым недостатком, который мешает полной ясности/доступности/убедительности; 0 — критерий применим, но выраженно не выполнен. Конкретные признаки 0/1/2 определены отдельно для каждого из 20 критериев (без сквозной формулы «худшего аспекта» и без жёстких количественных норм — оценка контекстная). Каждый балл агент обязан подтверждать конкретным наблюдением из текста, HTML или скриншота, с объяснением, почему наблюдение соответствует именно этому уровню. Полная шкала зафиксирована в `docs/cro-methodology.md`.
- Статус: согласовано с PM.

## 2026-08-10 — Финальное правило N/A vs 0

- Контекст: временное правило от 2026-08-08 оставляло открытым вопрос, должно ли отсутствие ожидаемого, но не найденного элемента (отзывы, кейсы, гарантия и т.п.) считаться N/A или 0. Вопрос был поставлен PM (`docs/questions-to-pm.md`).
- Решение (финальное, ответ PM получен): если критерий применим к конкретному лендингу и соответствующий элемент ожидается, но отсутствует, это считается проблемой и оценивается как **0**, а не N/A. N/A используется только в двух случаях: критерий объективно неприменим к данному типу предложения, либо его невозможно корректно оценить по доступным данным. Для каждого критерия сначала определяется применимость и ожидаемость элемента для конкретного лендинга, и только затем — присутствует ли он и в каком качестве. Правило пересмотрено во всех 20 критериях `docs/cro-methodology.md`, в первую очередь в блоке 3 («Доверие») и в критериях 4.1, 4.2.
- Статус: согласовано с PM, финально. Временное правило от 2026-08-08 и связанный открытый вопрос закрыты.

## 2026-08-10 — Анализ без скриншотов: данные отрендеренной страницы вместо изображений

- Контекст: черновик методики и технический каркас предполагали desktop- и mobile-скриншоты как источник данных для критериев, связанных с отображением страницы. Открытый вопрос про full-page/viewport был поставлен PM.
- Решение (финальное, ответ PM получен): сервис не создаёт и не анализирует скриншоты страницы. Анализ строится на коде и структуре страницы — включая данные отрендеренной страницы после выполнения JavaScript: итоговый DOM, видимый текст, computed styles, размеры и координаты элементов, видимость элементов, положение элементов относительно viewport, данные о desktop/mobile layout и другие структурированные данные. Это заменяет скриншоты как источник данных для визуально-зависимых критериев (расположение, перекрытия, обрезание элементов и т.п.) без создания изображений страницы. Все критерии `docs/cro-methodology.md`, ссылавшиеся на скриншоты (в частности блоки 1, 4, 5, 6), переформулированы под эту модель данных.
- Статус: согласовано с PM, финально. Открытый вопрос про full-page/viewport закрыт как неактуальный (скриншоты не используются вовсе).

## 2026-08-11 — Ozon 403 / antibot (FAB) при сборе страницы

- Контекст: `https://ozon.kz/...` на сервисе падал с «Страница недоступна (HTTP 403)». Причина: Ozon Fingerprint Antibot; `playwright.chromium.launch()` помечает сессию как автоматизацию, challenge не проходит; коллектор сразу считал HTTP 403 финальным отказом.
- Решение (наше техническое, точечный фикс): запуск Chromium отдельно и подключение через CDP (`connect_over_cdp`); после 403/challenge — ожидание авто-прохождения antibot; недоступность по 403 только если challenge не снят. Обычный `launch()` для сбора больше не используется.
- Уточнение после деплоя на Railway (SFO): с домашнего IP challenge проходит; с датацентрового egress Ozon показывает «нет соединения / выключите VPN» (`fab_chlg_*`) даже через CDP. Для таких хостингов опционально `COLLECTOR_PROXY_SERVER` (прокси для Chromium).
- Статус: наше техническое решение (зафиксировано командой).

## 2026-08-10 — Архитектура MVP-отчёта: один вызов LLM + overall на backend

- Контекст: нужно зафиксировать, кто формирует итоговый отчёт и как считается общая оценка, чтобы прогоны этапа 2 были воспроизводимыми и не зависели от «экспертного» усреднения моделью.
- Решение (наше архитектурное решение этапа 2, не решение PM):
  1. Используется **один вызов LLM**. Второй вызов для финального отчёта не применяется.
  2. LLM возвращает: все критерии (`score` / `justification` / `recommendation`), аналитику по блокам (`what_is_wrong`, `why_it_matters`), `problems`, `backlog`, и только `overall.summary` (2–3 содержательных предложения: что работает хорошо; основные проблемы; главный резерв улучшения). Summary не содержит числового score, не присваивает уровень `низкий/средний/высокий` и не агрегирует баллы.
  3. Backend валидирует ответ (6 блоков, ровно 20 ожидаемых criterion id без пропусков/дублей/неизвестных id), детерминированно считает overall и score каждого блока, собирает итоговый `AgentResult`. При ошибке валидации score не рассчитывается.
  4. Формула overall: `score = sum(applicable_scores) / (2 * applicable_count) * 100`; N/A исключается; округление до 1 знака; веса критериев одинаковые. Пороги: `<50` → `низкий`, `[50, 75)` → `средний`, `>=75` → `высокий`. При `applicable_count == 0` — ошибка расчёта. Сохраняются также `applicable_count` и `na_count`.
  5. Score блока — та же формула внутри блока. Если все критерии блока = N/A, `block.score = null` (не искусственный 0).
  6. Модели разделены минимально: `LlmAgentResult` (сырой ответ LLM, без numeric score) и `AgentResult` (итоговый результат со обязательными `overall.score`/`level` и `blocks[].score`). Расчёт — `app.agent.overall`, валидация — `app.agent.validation`.
  7. Формат MVP-отчёта: score/100 + level; summary; топ-3 backlog (без отдельной сущности); затем 6 блоков (score + what_is_wrong + why_it_matters + критерии); полный problems; полный backlog. Покрывает ТЗ 4.3 и 4.4 на уровне данных.
- Статус: наше архитектурное решение (зафиксировано командой для этапа 2).
