# Техническое задание

Анализатор конверсионности страниц

Версия 1.0 · Дата: 07.08.2026 · Постановщик: Marvis (PM) · Исполнитель: стажёр-разработчик

> Это рабочая текстовая копия исходного файла `tz_analizator_konversii.docx`. Содержание переносить без изменений; сам исходный файл не редактируется.

## 1. Зачем это нужно

Сейчас, чтобы понять, почему страница плохо конвертит (мало заявок, брошенные корзины, высокий отказ), нужно вручную открывать страницу, смотреть на неё глазами специалиста по конверсии (CRO) и записывать проблемы в отдельный документ. Это долго и зависит от того, кто именно смотрит.

Сервис должен взять на себя эту рутину: принять ссылку на страницу, прогнать её через агента, обученного оценивать конверсию по конкретной методике, и выдать понятный отчёт с готовым списком задач для команды.

## 2. Что видит пользователь (сценарий использования)

- Пользователь открывает веб-приложение и вставляет ссылку на страницу (например, лендинг или карточку товара).
- Нажимает «Анализировать».
- Сервис показывает статус выполнения (страница анализируется, это может занять 30–90 секунд).
- Пользователь получает отчёт на экране и может скачать его отдельным файлом.
- В этом же отчёте — готовый беклог задач: что именно поправить, чтобы конверсия выросла.

## 3. Из чего состоит сервис (архитектура на пальцах)

Три части, каждая отвечает за своё:

- **Фронтенд** — форма для ввода URL, экран статуса, экран с отчётом и кнопка «Скачать».
- **Бэкенд** — принимает URL, забирает содержимое страницы (текст, структуру, скриншот), передаёт агенту, сохраняет результат, отдаёт его фронтенду.
- **Агент-аналитик** — LLM с системным промптом, который содержит методику оценки конверсии (см. раздел 5). Агент получает данные о странице и возвращает структурированную оценку, а не свободный текст.

Технологии (язык, фреймворк, конкретная LLM) стажёр выбирает сам и согласовывает с PM перед стартом разработки. Важно не название стека, а то, что три части разделены и не завязаны друг на друга намертво — например, агента должно быть можно поменять на другую модель, не переписывая фронтенд.

## 4. Функциональные требования

### 4.1. Приём страницы

- Поле ввода URL с проверкой, что это корректная и доступная ссылка.
- Если страница недоступна (404, таймаут, требует авторизации) — понятная ошибка пользователю, а не «зависание».
- Сервис получает: HTML-структуру страницы, весь видимый текст, скриншот (десктоп и мобильная версия отдельно).

### 4.2. Работа агента-аналитика

- Агент анализирует страницу не «как получится», а строго по чек-листу методики (раздел 5) — по каждому пункту чек-листа агент обязан дать оценку и обоснование, ссылаясь на то, что он реально увидел на странице.
- Результат работы агента — структурированные данные (например, JSON: пункт чек-листа → оценка → пояснение → рекомендация), а не сплошной текст. Это нужно, чтобы бэкенд мог собрать из них таблицу и беклог, а не просто вставить текст в отчёт.
- Если агент не может оценить какой-то пункт (например, на странице нет отзывов и непонятно, планировались ли они) — он должен явно это пометить, а не придумывать оценку.

### 4.3. Отчёт

Отчёт должен состоять из следующих блоков:

- **Общая оценка страницы** — одна цифра или уровень (например, «конверсионный потенциал: средний»), плюс 2–3 предложения сути.
- **Оценка по блокам методики** — таблица: блок → оценка → что не так → почему это мешает конверсии.
- **Список найденных проблем** — конкретно, со ссылкой на то, где на странице это видно (текст, элемент, область скриншота).
- **Беклог задач** — см. раздел 4.4.

Отчёт должен открываться на экране и выгружаться отдельным файлом (формат файла — на усмотрение стажёра: PDF, HTML или Word; главное, чтобы отчёт можно было переслать коллеге без доступа к сервису).

### 4.4. Беклог задач

Отдельная таблица внутри отчёта со следующими колонками:

| Колонка | Что в ней | Пример | Обязательна |
|---|---|---|---|
| Задача | Конкретное действие | Добавить кнопку CTA выше первого экрана | Да |
| Зона страницы | Куда относится | Первый экран / форма / отзывы | Да |
| Приоритет | Высокий / средний / низкий | Высокий | Да |
| Ожидаемый эффект | Почему это должно поднять конверсию | Пользователь видит призыв к действию без скролла | Да |

Задачи в беклоге сортируются по приоритету (сначала высокий). Каждая задача — отдельная строка, без общих формулировок вроде «улучшить дизайн».

## 5. Методика оценки (то, чем руководствуется агент)

Готовой методики пока нет — её нужно разработать как часть этой задачи, до того как писать промпт для агента. Без неё агент будет каждый раз оценивать страницу произвольно, и отчёты нельзя будет сравнивать между собой.

Что нужно сделать:

- Составить чек-лист из конкретных, проверяемых пунктов (ориентир — 15–25 пунктов), сгруппированных по блокам. Примеры блоков: первый экран и оффер, понятность ценности продукта, доверие (отзывы, гарантии, кейсы), форма/CTA, мобильная версия, скорость и отвлекающие элементы.
- По каждому пункту чек-листа сформулировать: что именно проверяется, какая шкала оценки используется (например, 0–2: отсутствует / есть, но слабо / сделано хорошо), какой формулировкой агент должен объяснять свою оценку.
- Согласовать черновик чек-листа с PM перед тем, как встраивать его в промпт.
- Оформить чек-лист как системный промпт агента — так, чтобы агент не мог давать оценку в обход методики (то есть промпт явно требует пройти по всем пунктам, а не написать общее впечатление).

Это ключевое требование задачи: сервис не должен быть «спроси у ChatGPT, как улучшить сайт». Разница именно в том, что за агентом стоит зафиксированная методика, которую можно проверить, обсудить и улучшить отдельно от кода.

## 6. Технические требования

- Стек — на усмотрение стажёра, согласовать с PM до начала разработки.
- Системный промпт агента и чек-лист методики хранятся отдельным файлом/конфигом, а не зашиты в код — их должно быть можно поменять без деплоя новой версии бэкенда.
- Ключ от LLM-провайдера хранится в переменных окружения, не в коде и не в репозитории.
- Один анализ — один сохранённый результат (в базе или файлах), чтобы можно было вернуться к старому отчёту, не прогоняя анализ заново.
- Логирование ошибок: если анализ упал (страница не загрузилась, агент вернул невалидный ответ), это должно быть видно в логах, а пользователь должен увидеть понятное сообщение, а не пустой экран.

## 7. Что НЕ входит в задачу (на первой итерации)

- Массовый анализ (пакетная загрузка нескольких страниц за раз).
- Сравнение отчётов между собой во времени (история изменений одной страницы).
- Интеграция с рекламными кабинетами или аналитикой (GA, Яндекс.Метрика).
- Автоматическое внедрение рекомендаций на сайт.

Эти пункты можно закладывать в архитектуру заранее (не делать решений, которые их прямо исключают), но реализовывать не нужно.

## 8. Критерии приёмки (когда задача считается готовой)

- Есть согласованный чек-лист методики (раздел 5), оформленный как отдельный документ и как системный промпт агента.
- Пользователь может вставить произвольный публичный URL и получить отчёт без ручного вмешательства разработчика.
- Отчёт содержит все блоки из раздела 4.3, включая таблицу беклога с обязательными колонками.
- На трёх заранее выбранных тестовых страницах (разного качества — слабая, средняя, сильная) агент даёт разные и обоснованные оценки, а не одинаковый шаблонный ответ.
- Ошибки (недоступная страница, сбой агента) обрабатываются понятным сообщением, сервис не падает целиком.
- Отчёт можно скачать отдельным файлом.

## 9. Этапы

| Этап | Что делается | Результат |
|---|---|---|
| 1 | Разработка чек-листа методики и согласование с PM | Документ с методикой |
| 2 | Промпт агента + проверка на 3 тестовых страницах | Агент даёт структурированную оценку по чек-листу |
| 3 | Бэкенд: приём URL, сбор данных страницы, вызов агента, сохранение результата | Рабочий API |
| 4 | Фронтенд: форма ввода, статус, экран отчёта, выгрузка файла | Рабочий интерфейс |
| 5 | Сборка и проверка по критериям приёмки (раздел 8) | Готовый сервис |
